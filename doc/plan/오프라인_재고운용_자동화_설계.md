## 0. 왜 이 설계인가

### 이사님 피드백 핵심

> "현재 화면은 SERP의 또 다른 화면과 차이가 없다. LLM이 에이전틱하게 돌아갈 수 있는 시스템이 되어야 한다. 본사 사용자는 선택·선택·확정·확정 버튼 누르는 정도, 추후에는 사용자 없이 배치로 돌아갈 수 있는 확장성."

현재 보충배분-AIA의 문제는 **사용자가 판단을 해야 하는 위치**에 있다는 것이다. 스타일 네비게이터에서 어떤 스타일이 급한지를 사람이 파악해서 선택한다. AI가 판단해야 할 것을 사람이 하고 있다.

### 리오더 자동화에서 얻은 인사이트

리오더 자동화 시스템(AX팀, Seba)은 동일한 철학을 **발주(공급) 영역**에서 이미 구현 중이다:
- base-stock 공식으로 "이 스타일은 지금 몇 개 발주가 필요한가" 자동 계산
- priority ranking으로 "이번 주 뭐부터 봐야 하는가" 자동 정렬
- NarrativeCard로 "21개 중 4개 긴급" 한 줄 요약

우리는 이 구조를 **배분(분배) + RT(회전) 영역**에 동일하게 이식하면 된다.

- 보충배분: 이번 주 관점. "AP에 있는 재고를 어느 매장에 배분할 것인가"
- RT: 매장 간 이동. "상위 매장에 재고가 부족하면 하위 매장 것을 옮긴다"

## 3. Priority Scoring — 리오더 공식 이식 및 확장

### 3-1. 리오더 시스템의 공식 (기준)

```
Priority = 0.40 × urgency + 0.40 × risk_gap + 0.20 × confidence
```

| 축 | 산식 | 의미 |
|---|---|---|
| urgency | `min(1, lead_time / max(1, season_weeks_remaining))` | 시즌 끝 대비 리드타임 압박 |
| risk_gap | `clamp(0,1, (OPT-EOI)/OPT) × log10(1 + sale_volume)` | 재고 부족 × 판매 규모 |
| confidence | `1 - (ci_high - ci_low) / ml_value` | 예측 신뢰도 |

### 3-2. 보충배분 적용 버전 (v2 — 2026-06-04 재설계)

> **v1→v2 변경 이유 (2026-06-02 이사님 피드백)**
>
> v1은 "AP 창고 커버리지"가 출발점이었으나, 올바른 출발점은 **"매장 재고 부족"**이다.
> 매장이 넉넉한데 AP가 적은 건 긴급이 아니고, AP가 많아도 매장이 비면 즉시 보충해야 한다.
> "매장재고가 부족할 때 창고에 줄 재고가 있으면 긴급보충, 창고에 없으면 RT"

**v2 핵심 구조:**

```
Step 0: 미입고 SC 필터 — 매장 재고 ≈ 0 + 최근 판매 0 → initial (초기 배분)
Step 1: 매장이 부족한가? — 부족 비율 ≥ 30%
  ├─ Yes + AP > 0  → 🔴 urgent (긴급 보충: 창고→매장)
  └─ Yes + AP = 0  → 🔄 rt (매장→매장 이동)
Step 2: 곧 부족해질 것인가? — 속도 +40%↑ AND 평균 재고주수 3~5주
  └─ Yes → 📈 trend (급상승: 선제 대응)
Step 3: 위 해당 없음 → ⚪ normal
```

**매장별 재고주수 계산 (분류의 핵심):**
```
매장_재고주수 = 매장_현재고 / PRED_SH_SC_W
부족_매장 = 재고주수 < 3주인 매장 수
부족_비율 = 부족_매장 / 전체_매장
```
- 매장 현재고: `DW_SH_SCS_DACUM` (사이즈 합산, 창고 제외)
- 매장별 SC 예측: `FNF.ML_DIST.PRED_SH_SC_W` — `PRED_SH_SC_QTY`, `MAX(EXECUTION_DT)` 기준
- 3주 기준: 매장이 3주 미만 재고를 보유하면 "부족"으로 판정
- 상위 매장 가중치 없음 — 모든 매장 동등하게 취급

**Priority Score (v2):**

```
SC_Priority = 0.50 × shortage_ratio
            + 0.30 × velocity_signal
            + 0.20 × ap_pressure
```

| 축 | 산식 | 데이터 소스 | 의미 |
|---|---|---|---|
| **shortage_ratio** | `부족매장수 / 전체매장수` (0~1) | DW_SH_SCS_DACUM + PRED_SH_SC_W | 매장 부족 비율 — 높을수록 긴급 |
| **velocity_signal** | `clamp(0, 1, velocity_change_pct / 50)` (50%=1.0) | BIM_SHOP_DD_STK 최근 2주 vs 전전 2주 | 판매 가속도 |
| **ap_pressure** | `clamp(0, 1, 1 - AP커버주수 / 3)` | AP재고 / PRED_SC_W | AP 소진 압박 — 보충 시 AP가 부족한 정도 |

> **v1과의 차이**: v1은 coverage_urgency(0.40)와 rt_score(0.40)에 AP 재고를 이중 반영했음.
> v2는 shortage_ratio(매장 부족)가 주축(0.50)이고, 분류는 if/else로 결정되므로 priority_score는 같은 분류 내 정렬 순서에만 사용.

**파라미터:**

| 파라미터 | 값 | 비고 |
|---|---|---|
| `SHOP_SHORTAGE_WEEKS` | 3.0주 | 매장 부족 판정 기준 |
| `SHORTAGE_RATIO_THRESHOLD` | 0.30 (30%) | ⚠️ 테스트 필요 — 실 운영 후 조정 |
| `VELOCITY_SURGE_PCT` | 40% | 급상승 판정 속도 기준 |
| `SURGE_COVERAGE_MIN/MAX` | 3~5주 | 급상승 판정 재고 범위 |
| `INITIAL_AVG_INV_WEEKS_MAX` | 0.5주 | 미입고 필터 |
| `INITIAL_VELOCITY_FLOOR` | -90% | 미입고 필터 |

**실행 결과 (2026-06-04, Discovery 26S, 1,502개 SC):**

| 분류 | 개수 | 비율 |
|---|---|---|
| 🔴 긴급 보충 | 38 | 2.5% |
| 🔄 RT 대상 | 1 | 0.1% |
| 📈 급상승 | 5 | 0.3% |
| 🆕 미입고 | 2 | 0.1% |
| ⚪ 정상 | 1,456 | 97.0% |

### 3-3. RT 분류 — v2 단순화

> **설계 원칙 (2026-05-29 확정, 2026-06-04 v2 반영)**
>
> 화면 0의 역할은 "RT를 돌릴 가치가 있는 SC가 어느 것인가"를 찾는 것이다.
> 어느 매장→어느 매장으로 이동할지는 별도 단계에서 결정하며, 화면 0에서 다루지 않는다.

**v2에서 RT 판정:**

```
매장 부족 비율 ≥ 30% AND AP 재고 = 0 → RT
```

- v1의 CV(불균등도) 계산과 donor 존재 체크는 **제거**
- 이유: v2의 출발점이 "매장이 부족한가"이므로, 부족한데 창고가 비면 RT가 유일한 선택지
- Phase 2에서 RT 실행 단계에 donor 존재 체크 추가 예정

<details>
<summary>v1 rt_score 참조 (퇴역 예정)</summary>

v1에서는 `rt_score = ap_shortage × distribution_imbalance` 곱셈 구조로, AP 부족도와 매장 CV(변동계수)를 조합했음. v2에서는 매장 부족 비율이 분류의 핵심이므로 별도 rt_score 계산 없이 AP 유무만으로 판정.

</details>

### 3-4. 카테고리별 분류 기준 (v2)

| 분류 | 기준 | signal_type | 조치 |
|---|---|---|---|
| 🆕 미입고 | `avg_inv_weeks ≤ 0.5` AND `velocity ≤ -90%` AND `부족비율 ≥ 30%` | `initial` | 초기 배분 (긴급 보충과 구분) |
| 🔴 긴급 보충 | `부족비율 ≥ 30%` AND `AP > 0` | `urgent` | 즉시 보충배분 (AP→매장) |
| 🔄 RT 대상 | `부족비율 ≥ 30%` AND `AP = 0` | `rt` | 매장 간 이동 검토 |
| 📈 급상승 | `velocity ≥ +40%` AND `avg_inv_weeks 3~5주` | `trend` | 선제 모니터링 / 배분 준비 |
| ⚪ 정상 | 위 해당 없음 | `normal` | 자동 관찰 |

> RT 대상 SC에 대해 "어느 매장 → 어느 매장"은 화면 0에서 표시하지 않는다.
> 사용자가 해당 SC를 선택해 배분 화면으로 진입하면, 그 시점에 매장 재고 기반으로 source/destination을 계산한다.

#### 리오더 자동화의 3가지 텍스트 생성 지점

| 위치 | 생성 방식 | 예시 출력 |
|---|---|---|

| `handlers.py` `_signal_reason()` | `signal_level + reorder 유무 + recovery_ws` if·elif | `"결품 임박 → 발주 후 회복"` / `"buffer 부족 — 발주 권장"` / `"과재고 — 발주 보류"` |

#### 우리 `scoring_engine.py`에서의 `ai_reason` 생성 방식

**Phase 1 — 룰 기반 템플릿 (리오더와 동일 방식)**

```python
def build_ai_reason(
    coverage_weeks: float,
    broken_shops: int,
    broken_sizes: list[str],
    velocity_change_pct: float,
    ap_stock: int,
    signal_type: str,
) -> str:
    """수치 기반 한국어 안내 문자열 — LLM 없음, 순수 f-string."""
    size_str = "·".join(broken_sizes) if broken_sizes else ""
    
    if signal_type == "urgent":
        parts = []
        if broken_shops > 0 and size_str:
            parts.append(f"상위 {broken_shops}개 매장 {size_str} 사이즈 소진")
        elif broken_shops > 0:
            parts.append(f"상위 {broken_shops}개 매장 재고 부족")
        parts.append(f"AP {ap_stock}개 기준 {coverage_weeks:.1f}주 커버")
        if velocity_change_pct >= 10:
            parts.append(f"판매속도 +{velocity_change_pct:.0f}% 상승 중")
        return ". ".join(parts) + "."

    if signal_type == "rt":
        return (
            f"하위 매장 과잉 재고 — 상위 {broken_shops}개 매장으로 RT 권장. "
            f"이동 시 {coverage_weeks:.1f}주 → 균등 분산 가능."
        )
    if signal_type == "trend":
        return f"판매속도 전주比 +{velocity_change_pct:.0f}% 가속. 선제 배분으로 결품 예방."
    return "안정"
```

출력 예시:
- `urgent` → `"상위 11개 매장 M·L 사이즈 소진. AP 23개 기준 0.4주 커버. 판매속도 +47% 상승 중."`
- `rt` → `"하위 매장 과잉 재고 — 상위 5개 매장으로 RT 권장. 이동 시 2.1주 → 균등 분산 가능."`
- `trend` → `"판매속도 전주比 +31% 가속. 선제 배분으로 결품 예방."`

**Phase 2+ — LLM 대체 (인터페이스 변경 없음)**

```python
# Phase 1: 룰 기반
ai_reason = build_ai_reason(coverage_weeks, broken_shops, ...)

# Phase 2+: LLM 대체 — 반환 타입 동일 (str), 호출부 코드 변경 없음
ai_reason = call_llm_reason(
    prompt_template="SC {sc_cd} 상태를 한 문장으로 설명하라. 수치: {metrics}",
    metrics={"coverage_weeks": coverage_weeks, "broken_shops": broken_shops, ...}
)
```

> **원칙**: Phase 1에서 LLM을 쓰지 않아도 "에이전틱"으로 보이는 이유는 텍스트가 아니라 **자동 우선순위 정렬 + 체크박스 일괄 선택**이 핵심이기 때문. 텍스트 품질은 Phase 2에서 높인다.

## 7-B. 화면 0 데이터 전략

### 핵심 질문: 화면 1·2와 어떻게 다른가

**화면 A/B의 데이터 패턴**:
```
사용자가 스타일 직접 선택 → 조회하기 클릭
  → 선택한 SC N개에 대해서만 API 호출
  → /api/forecast, /api/warehouse-stock, /api/shop-stock
```
→ "내가 고른 것만" 가져온다. 조회 범위가 작다.

**화면 0의 데이터 패턴**:
```
화면 진입 시 또는 조회하기 클릭
  → 필터 조건(브랜드, 시즌) 해당 SC 전체 (200~300개)에 대해
  → 긴급도 점수를 계산해서 보여줘야 한다
```
→ "전체를 미리 훑어서" 우선순위를 보여준다. 조회 범위가 크다.

이 차이 때문에 화면 A/B의 실시간 API 패턴을 그대로 쓰면 **문제가 된다**:
- SC 300개 × SERP API 3회 = 900번 API 호출 → 타임아웃, 비용 폭발
- PRED_SC_W도 300개 동시 조회 → 느림

### C-3. [AP 재고 업데이트] 버튼 상세 설계

**위치**: 화면 0 상단 헤더, "마지막 배치" 타임스탬프 옆

**동작 흐름**:
1. 버튼 클릭 → 로딩 스피너 표시
2. `/api/refresh-ap-stock` POST 호출
   - body: `{ brandCd, ssnCd, apCd, scList: [{prodCd, colorCd}, ...] }`
   - scList = 현재 briefing에서 signal_type이 urgent/rt/trend인 SC만 (normal 제외)
3. API Route 내부:
   - scList 순회, 각 SC에 대해 DRP API `ap-stk` 호출 (병렬 처리)
   - 결과: `{ stocks: [{prodCd, colorCd, apStock}] }`
4. 프론트에서 briefing 데이터의 ap_stock 값 교체
5. signal_type 재계산 (urgent ↔ rt 전환 가능)
   - AP가 소진되었으면 urgent → rt로 변경
   - AP가 새로 입고되었으면 rt → urgent로 변경
6. 카드 갱신 + "업데이트: HH:MM" 타임스탬프 갱신

**재계산 로직**: 프론트에서 간단히 수행 (scoring_engine의 is_urgent/is_rt 조건과 동일):
```typescript
function reclassify(sc: BriefingSC, newApStock: number): SignalType {
  const isUrgent = newApStock >= 10 && sc.broken_shops >= 5 
    && sc.weekly_forecast >= 10 && sc.coverage_weeks < 1.0 
    && sc.velocity_change_pct >= -50;
  const isRt = !isUrgent && newApStock === 0 
    && sc.broken_shops >= 20 && sc.weekly_forecast >= 10 
    && sc.velocity_change_pct >= -50;
  if (isUrgent) return 'urgent';
  if (isRt) return 'rt';
  return sc.signal_type; // 변경 없음
}
```
